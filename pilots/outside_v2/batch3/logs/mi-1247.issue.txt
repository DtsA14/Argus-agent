numeric_range: len(), `in` and index() disagree with the items produced, for float steps

`numeric_range` derives `len()`, `__contains__` and `index()` by dividing by the step, but produces its items by repeated multiplication. With floats the two disagree, so a range can report a length that does not match what it yields, and can deny membership to its own items.

On 11.1.0 and on current master (`2fe1b2e`):

### `len()` disagrees with iteration, in both directions

```pycon
>>> from more_itertools import numeric_range

>>> r = numeric_range(-8.732, -13.532, -2.4)
>>> list(r)
[-8.732, -11.132]
>>> len(r)
3
>>> r[2]                      # counted, but it is the excluded stop value
-13.532

>>> r = numeric_range(-69.37276490678778, -29.8339073344664, 4.942357196540172)
>>> len(list(r))
9
>>> len(r)
8
>>> r[8]                      # an item iteration yields, but indexing cannot reach
IndexError: numeric range object index out of range
```

### Items are not `in` their own range

```pycon
>>> r = numeric_range(0.0, 1.0, 0.1)
>>> r[3]
0.30000000000000004
>>> r[3] in r
False
>>> r.index(r[3])
ValueError: 0.30000000000000004 is not in numeric range
>>> sum(1 for v in r if v not in r)
5
```

`count()` follows `__contains__`, so it returns 0 for those items too.

### Cause

`__iter__` and `_get_by_index` compute items as `start + n * step`. Membership and length instead reason about the step arithmetically:

- `__contains__` and `index` test `(value - start) % step == 0`. `0.30000000000000004` is what the range yields at index 3, but it is not an exact multiple of `0.1`, so the remainder is not zero.
- `_len` computes `divmod(distance, step)` and rounds up. That measures the distance to cover rather than counting the items actually produced, and lands one over or one under when the multiplication does not agree with the division.

Exact types are unaffected — `Decimal`, `Fraction`, `int`, and `datetime`/`timedelta` all give a zero remainder for their own items, so they behave the same before and after. This is specific to binary floats.

The `__contains__` shortcut dates to #363 (2020); `_len` has had the same shape since it was introduced.

### Note

This is not only about surprising float repr, which the docstring already warns about. `numeric_range` is a `Sequence`, and here `r[i] not in r` and `len(r) != len(list(r))` — the object disagrees with itself, so `.index()`, `.count()`, `in`, `len()` and indexing give inconsistent answers for the same range.

I have a fix that settles all four against the items the range actually produces, keeping the exact-type behavior and the current performance for them. Happy to open a PR if you would like it.
